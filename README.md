# Aegis

Aegis is a Go control plane for authenticated, trust-stanza-bound sessions over an explicit Hermes Agent runtime. It does not hide Hermes, infer authority from prompts, or treat the model as an approver or provisioner.

Its security contract is: identity and authority are established outside the model; prompts, profile names, model conclusions, and stanza requests are not authentication. Each runtime session binds to exactly one authenticated trust stanza. Trust stanzas are security contexts, not personalities: zero or multiple authorized matches deny, grants are never unioned, and a stanza or material-authority change requires a new mandate and clean session.

The implemented fleet-control MVI is Agent Registry → immutable Loop revision → immutable Graph revision → authority-bound Execution Queue → evidence-gated disposition. Execution Queue lifecycle is controlled manually through principal-authenticated controller-side primitives: bounded retry/reclaim on the same `GraphRun`/`LoopExecution` with a new numbered attempt, terminal `cancel`/`expire`/`exhaust`/`revoke`, exact queue-authority admission repeated at every consequential boundary, ≤ 24h retry backoff, pinned `MaxAttempts` budget, and a complete ordered historical readback. Cancelled, expired, exhausted, revoked, denied, failed, and succeeded outcomes remain distinct durable vocabulary; live (non-expired) retry, reclaim without an expired lease, retry beyond the attempt budget, and terminal replay all deny. The authenticated browser queue inspector can process claimable work, reclaim an expired lease, or request a terminal lifecycle transition through a closed same-origin CSRF-protected form. The server reloads the exact queue item, derives authority and all operation identifiers server-side, repeats fresh admission, and returns distinct fail-closed denial codes; browser state itself grants no authority. No automated retry/reclaim/expiry/revocation scheduling and no distributed scheduler exist. A shared internal reference layer provides validated, versioned identity/digest and identity/revision/digest bindings with strict deterministic JSON codecs; these primitives carry no authority. `internal/registry`, `internal/loop`, `internal/graph`, `internal/queue`, and `internal/execution` own bounded canonical definitions and lifecycle records, while the Badger `fleet-v1` adapter atomically persists immutable definitions, accepted or durably rejected submissions, dependency-gated attempt-bounded claims, expired-lease retry/reclaim, queued-or-claimed cancellation, rebuildable queue projections, content-addressed evidence, and terminal disposition with repository-assigned hash-linked audit facts. Graph publication and submission resolve every pinned Loop revision and require each node's exact input/output port names, types, and required flags to match that immutable Loop interface; publication denies a mismatch, and submission records a durable rejection rather than queueing incompatible work. Shared application services bind principal-authenticated CLI and HTTP requests to one freshly admitted exact authority context. Public `agents`, `loops`, `graphs`, and `queue` CLI resources and protected `/v1/agents`, `/v1/loops`, `/v1/graphs`, `/v1/submissions`, and `/v1/queue` routes expose the narrow vertical, including exact historical reads, Graph lifecycle and accepted/rejected submission history, and registered runtime-routed queue processing with bounded Hermes gateway turns. The authenticated Execution Queue console follows the retained OpenDesign structure with exact execution routes and separately renders queue/runtime identity, Graph/Loop/attempt causality, ordered lifecycle timeline, claim/retry/cancellation records, dependent-loop outcomes, artifacts, verifier receipts, and terminal disposition without deriving success from process or receipt output. ## Install and update

Tagged releases use stable Semantic Versioning tags (`vMAJOR.MINOR.PATCH`). Install directly with Go:

```sh
go install github.com/berryhill/aegis/cmd/aegis@latest
```

Alternatively, download the matching archive and `SHA256SUMS` from the GitHub release. Release archives support Linux and macOS on amd64 and arm64. Releases also publish one deterministic, source-revision-bound `aegis-skills_vVERSION.tar.gz` archive for the [official Hermes skill suite](docs/HERMES_SKILLS.md); installing a skill remains a separate explicit Hermes-profile action. The release workflow and ordinary CI use the same repository-owned `scripts/verify-installed-mvi.sh` path to require an exact clean Git commit, build all four binary archives plus the skill bundle, require each binary archive to contain exactly one root `aegis` regular file with mode `0755`, validate and evaluate the skill source, verify the deterministic skill archive inventory and provenance, verify `SHA256SUMS`, reject missing, dirty, malformed, or mismatched Go VCS metadata, extract the native binary archive, and check its injected stable version and exact embedded source revision before running the credential-independent fleet vertical through the real bounded Hermes adapter against a protocol-faithful fake gateway. This repository verification does not itself publish a release or prove live-provider/model acceptance. A release-archive installation can check for or atomically install the latest published release:

Before publication, maintainers can run the separately gated `scripts/verify-release-candidate.sh` against an explicit clean source revision, supported Hermes executable, empty repository-local evidence workspace, and exact operator-authored decision JSON. It builds once, verifies that the resulting binary exposes the same exact embedded source revision, reuses one digest-bound native candidate, rehearses rollback and local-staging withdrawal, and records that no publication or production installation was mutated. The decision record is evidence of supplied intent, not authentication or publication authorization; `make release` remains the separate operator-controlled publication transaction. See the quickstart for the exact schema and invocation.

```sh
aegis update --check
aegis update
aegis --update
```

`aegis --update` is a strict root-only alias for `aegis update`; ambiguous combinations with subcommands or other root actions are rejected. Both forms use the same checksum-verifying updater before atomically replacing the exact current executable. Package-manager-owned or non-writable executables should be updated through their original installation method.

The updater selects only the latest exact published stable GitHub release and fails closed if its repository identity, publication metadata, archive, or matching `SHA256SUMS` entry is unavailable or invalid. A local or remote Git tag alone is not an available update; the tag-triggered workflow must finish publishing the GitHub release.

## Build

```sh
go build -o aegis ./cmd/aegis
```

Go 1.26.6 or newer is required. `aegis version` and `aegis --version` print the same build version without requiring configuration. The application uses Cobra, isolated Viper instances, Echo v5, context cancellation, and injected `log/slog` loggers. Executables built into the verified source checkout report `dev` and are mechanically bound to the ignored `<repository>/.aegis` profile beside `./aegis`, even when Go embeds the checkout's clean release tag as its module version. Tagged release archives and stable versioned `go install` binaries outside a worktree use the `production` profile at `~/.aegis`. Each profile has separate configuration, encrypted authority, deployment identifier, audit/checkpoint state, manager certification, and runtime state. Development refuses paths outside its verified repository profile, and destructive reset is restricted to each binary's own exact profile layout.

## Configure

For a new release installation, run bare installed `aegis` in a terminal or run `aegis init`. Its literal production root is `~/.aegis`: configuration is `~/.aegis/aegis.yaml` and state is `~/.aegis/state`. A repository-built `./aegis` uses the same directory name only beneath the verified repository root, visibly reports the development profile, and cannot resolve the home production root. The development executable must remain beside this repository's real `go.mod` and `.git` in a checkout below the authenticated operator home; a copied `dev` binary fails closed. A former production `~/.argis` tree and prior XDG defaults are migration inputs only: an old-only installation requires explicit migration, while meaningful canonical/former/XDG coexistence fails closed before mutation. A pre-rename repository `.aegis-dev` tree is likewise denied rather than silently orphaned or merged. XDG variables do not scatter either profile. Aegis verifies the current UID/username through host-native account APIs, displays the exact resolved paths plus complete configuration content, and writes only after the operator types `yes`. Profile and state roots are mode `0700`; initialization first publishes and verifies an empty generation-managed Badger authority at `state/persistence/authority-v1`, then revalidates operator identity and atomically publishes configuration mode `0600`. Interruption before configuration publication is resumable only when that authority remains valid and empty. Populated or unsafe legacy `mandates`, `authority-contexts`, `authority-revocations`, or `sessions` paths deny before either publication and are never imported. Initialization does not invoke Hermes, Ollama, a model, cloud service, credential creation, provisioning, or profile modification. See [Local Path Layout](docs/PATH_LAYOUT.md).

The internal Badger authority maintenance API serializes initialization, open-store lifetimes, export, import, activation, rollback, recovery, projection rebuild, and garbage collection across cooperating Aegis processes. Qualified Linux lifecycle and maintenance mutations are anchored to no-follow directory descriptors, and initialization plus candidate-producing maintenance preserves a fixed 256 MiB disk reserve. Maintenance runs only against one closed, clean, identity-verified active generation. Export creates a bounded mode-`0600` backup without replacing its destination. Logical recovery verifies and imports canonical records into a fresh inactive generation, omits stored derived authority projections, and rebuilds them from canonical command/fact replay; it does not activate the result. Native recovery requires the caller to name an exact verified retained generation. Activation, native recovery, and rollback return a typed outcome that distinguishes failure before durable selection from committed selection whose prior-generation retirement or later durability work failed. Garbage collection revalidates captured directory identity and removes only through descriptor-relative no-follow traversal; it refuses unknown or ambiguous entries and never removes the active generation. Backup SHA-256 metadata detects modification relative to the manifest, but the backup is neither encrypted nor cryptographically signed. This is currently an internal persistence surface, not a CLI or HTTP workflow.

The post-Track-A persistence qualification is narrower than the release build matrix. Session authority, fleet-control definitions, and fleet-control lifecycle are qualified on Badger `v4.9.5`, while credential custody is qualified on bbolt `v1.5.0`, only for the exact Linux/amd64/ext4 single-Aegis-process combinations in [the storage specification](specs/STORAGE.md). Both fleet planes are fixed to schema `fleet-v1` in one shared `state/persistence/fleet-v1` store with an exclusive writer lock, synchronous conflict-detecting writes, mode-`0700` directories, mode-`0600` files, a 256 MiB free-space reserve, and clean-or-verified-recovered readiness. The adapter implements atomic accepted-or-rejected submission, dependency-gated attempt-bounded claims, expired-lease retry/reclaim with bounded backoff, queued-or-claimed cancellation, validated rebuildable projections, and terminal evidence/disposition persistence. The public application boundary and installed no-key vertical exercise the narrow accepted/rejected submission, claim, registered Hermes gateway-turn, evidence, and terminal path with fresh admission at each consequential boundary. Migration/backup/recovery tooling, dirty-store recovery, automated lifecycle scheduling, multi-node scheduling, and live-provider acceptance remain unimplemented. macOS and arm64 archives are build/checksum outputs, not storage-qualification evidence, and the installed proof does not broaden qualification beyond Linux/amd64/ext4. Canonical facts, rebuildable projections, operational metadata, blobs, runtime state, and credential custody remain separate; derived state and cross-store partial results never grant authority.

For an explicit example configuration, copy it, set restrictive permissions, replace the principal placeholders, and make the matching replacement in `examples/office-charter.json`:

```sh
cp examples/aegis.yaml .aegis.yaml
chmod 600 .aegis.yaml
transport_dir=$(pwd -P)/.aegis/transport
install -d -m 700 "$transport_dir"
python3 - "$transport_dir/api.token" <<'PY'
import pathlib, secrets, sys
path = pathlib.Path(sys.argv[1])
path.write_text(secrets.token_hex(32) + "\n", encoding="ascii")
path.chmod(0o600)
PY

```

An explicit valid configuration is not itself operational authority. If its configured state directory has no `persistence/authority-v1`, ordinary commands and every non-interactive entry point fail with `operational_authority_not_initialized` and exit 2 without creating state. Run `./aegis --config .aegis.yaml init` in a real terminal, review the freshly authenticated UID/username and exact authority path, and type `y` or `yes` at the default-deny reconciliation prompt. Only exact absence may create one secure empty generation. Existing markerless, dirty, corrupt, symlinked, wrong-owner, insecure, ambiguous, or populated legacy state is preserved and denied for operator repair; it is never replaced. Repeating initialization or running `agents list` after reconciliation preserves the selected generation identity.

The binding is mandatory. Precedence is:

1. CLI flags
2. `AEGIS_*` environment variables
3. Explicit config file
4. compiled defaults

`api.token_file` must name an absolute, current-owner, mode-`0600`, single-link regular file containing at least 256 bits of encoded transport material. Aegis reads it at startup and redacts the loaded token in `aegis config`; inline `api.token` remains supported for compatibility but must not be used for new service onboarding. The token authenticates API transport and never replaces local OS or Unix-peer principal authentication.

## Authenticated gateway and console

On an initialized development or production installation, bare interactive `aegis` reconciles an absent transport only after showing the exact configuration digests, absolute generated token-file path, and Unix-socket path and receiving conventional `[Y/n]` confirmation. It then previews one deterministic `systemd --user` gateway unit and requests a separate `[Y/n]` confirmation before installation and activation. Both prompts accept Enter, `y`, or `yes`; every other answer, EOF, cancellation, or input failure declines without mutation. After that first successful activation and authenticated readiness check, the same process enters the authenticated Aegis agent terminal directly. On later invocations Aegis classifies startup before opening operational persistence: it verifies the installed unit bytes, systemd's loaded fragment, the loaded `ExecStart` executable and complete `serve --config` arguments, observed activity, and authenticated audit-current `/readyz`, then enters the same gateway-backed agent directly without an intermediate action chooser or browser launch. Recovery of an exact gateway whose state root was recreated validates the loaded fragment and complete `ExecStart` before lifecycle mutation, restarts it so the process binds the recreated state, and revalidates both loaded identities before authenticated readiness. A stale or foreign loaded definition therefore cannot be executed as recovery. The terminal client authenticates each request with the protected Unix transport, receives one short-lived in-memory session bound to the authenticated principal and one `secrets-manager` stanza, and executes typed commands through the gateway's sole application service. Missing, expired, revoked, interrupted, or mismatched transport/session authority fails closed without direct-store fallback. The browser console remains a separately password-authenticated presentation surface available through explicit `aegis console`; it is not part of bare startup and does not establish principal authority.

Use the explicit lifecycle commands when desired:

```sh
aegis gateway preview
aegis gateway install
aegis gateway status
aegis gateway start
aegis gateway stop
aegis gateway restart
aegis gateway uninstall
aegis console
aegis manager
```

`aegis service` is a compatibility alias for `aegis gateway`; it delegates to the same lifecycle implementation and does not create a second authority surface.

`preview` reports the exact unit path, executable/configuration paths, console origin, and SHA-256 unit digest without reusable bearer material. Install reauthenticates the configured UID/username, revalidates the complete approved plan immediately before mutation, refuses any existing unit that is not a current-owner single-link regular file with exactly the expected bytes, and activates through explicit publish, daemon-reload, enable/start, exact loaded-fragment validation, and authenticated audit-current readiness phases. A failed phase names the phase and retains readiness and rollback diagnostics. Rollback removes only a unit newly published by that install and reverses only gateway state that operation introduced; pre-existing exact unit bytes and pre-existing active/enabled state are preserved. Status reports `systemctl --user` activity and observed linger state; Aegis does not change linger and claims logout survival only when the host already reports it enabled. Before invoking `systemctl`, start/stop/restart require the exact current Aegis-owned unit; when it is absent they return `gateway_not_installed` and name `aegis gateway install` without installing or changing gateway state. They report success only after the loaded fragment still resolves to the approved unit: start/restart also require observed active state and authenticated audit-current readiness, while stop requires observed inactivity. A pending but verifiable audit projection is advanced only through the protected bounded audit-delivery endpoint before readiness is retried. Successful lifecycle commands return a typed result containing the action, unit path/digest, observed activity, and applicable readiness fields. Install and uninstall require terminal confirmation; uninstall disables and removes only the exact digest-bound Aegis-owned unit and preserves configuration, state, and external credentials.

The daemon acquires an owner-only nonblocking singleton lock at `<unix_socket>.lock` before inspecting or removing a stale owned socket. A second daemon therefore denies before socket mutation. The gateway remains a same-UID boundary, not isolation from another process under that account, root, or the kernel, and the unit's `NoNewPrivileges=true` is not a sandbox. Bare development and production `aegis` do not open a browser after readiness; they enter the authenticated agent terminal directly. Explicit `aegis console` reports the clean configured `/console` URL and `principal_password` requirement without launching a browser, issuing authentication material, or creating a session. The browser must submit the enrolled principal password through the exact-origin login form; only successful verification creates the bounded host-only `HttpOnly`, `SameSite=Strict`, origin-appropriate `Secure` cookie. Missing, malformed, incorrect, oversized, unavailable, or throttled password verification fails closed without a session cookie.

## End-to-end workflow

After the authenticated onboarding prerequisites reach `Ready`, fresh and resumed bootstrap presents a separate default-decline approval for one canonical built-in Agent named `aegis`. Approval creates exactly revision 1 with Aegis product ownership, the authenticated principal as the accountable party, source kind `aegis-system`, and runtime target `manager-disposable`; exact replay is idempotent, any collision denies, and bootstrap reports success only after complete registration/revision readback. Here `agent_id=aegis` is a logical Agent Registry identity and `runtime_target=manager-disposable` is a disposable runtime contract, not a named Hermes profile. Registration never creates `~/.hermes/profiles/aegis`; launch through bare `aegis` or `aegis manager`, not `hermes --profile aegis`. The sealed record grants neither credential access nor model/runtime authority and does not read or inherit normal `~/.hermes`. A gateway already running from before this feature continues to own its stores and is not silently backfilled; a future gateway-owned, explicitly approved backfill is still required for that residual case.

Bare interactive `aegis` and explicit `aegis init` invoke the same complete artifact-derived onboarding state machine. Fresh bare startup creates or resumes principal configuration, operational authority, credential authority, Hermes/local Ollama runtime verification, exact model binding, and end-to-end certification through the same separate approvals; declining or failing any stage stops before gateway or manager activation and resumes from verified artifacts on the next invocation. Only a `Ready` onboarding snapshot may proceed through the separately approved gateway/readiness path and enter the authenticated conversational Aegis agent terminal directly. An active session requires the exact configured and certified local model, starts one clean disposable Hermes Agent session under the authenticated principal, one `secrets-manager` stanza, and one short-lived mandate, and routes ordinary text through the gateway-owned bounded manager ingress. Missing or invalid model, certification, credential authority, Hermes, Ollama, route, or process-custody evidence leaves slash controls available but denies ordinary conversation without a cloud or alternate-model fallback. Explicit `aegis init` continues the resumable manager-onboarding journey. That journey identifies `basic` as the default presentation and shows one recommendation plus its plain-language consequence at a time. Before each presentation-owned consequential approval, enter `details` or `advanced` to reveal exact paths, endpoint, custody, digest, certification, or gateway evidence; enter `basic` to return to the concise view. These are presentation depths over the same trust path—not separate provisioners, trust levels, defaults, state machines, or authorization policies—and changing depth cannot advance or reset work. The opening screen states that it is setting up one authenticated exact-local manager, that the model never chooses or authorizes a step, and that the operator may exit at any prompt and rerun `aegis init`. Five artifact-derived manager-onboarding stages—local identity/configuration, credential authority, Hermes/local Ollama runtime, exact model binding, and end-to-end certification—show completed, current, and remaining progress during bare or explicit initialization. Verified stages are summarized instead of replayed, and explicit `aegis init` resumes at the first incomplete artifact rather than a stored wizard cursor. Certification states its potentially substantial CPU/GPU/RAM/time cost before approval; decline, EOF, or interruption writes no certification and a later explicit initialization resumes from verified artifacts. Once principal and operational authority are ready, profile dispatch is explicit: after fresh activation, bare development and production `aegis` ensure the approved gateway is authentically ready and enter the authenticated Aegis agent terminal directly; explicit `aegis manager` enters that same terminal client. A manager with absent or invalid certification remains degraded, disables conversational inference, reports the exact certification reason and configured-candidate recertification command, retains deterministic local controls, and attempts no cloud or alternate model. A genuinely absent installation still mutates only after exact preview and conventional `[Y/n]` confirmation; an older valid configuration with exact operational-authority absence still requires its separate default-deny confirmation. An inference-capable manager session starts only after every prerequisite passes; with ready authority but absent or invalid certification, explicit manager startup remains in the authenticated degraded shell described above. Bare non-TTY use never prompts or mutates: it emits a structured state/reason/next-command payload and exits 2. Ordinary commands also deny rather than implicitly initializing missing operational authority. Existing malformed, insecurely permissioned, partial, drifted, or ambiguous artifacts enter a repair-required path and are never treated as absent or silently overwritten. The manager authenticates the configured OS principal and starts one Aegis-owned terminal controller. A persistent authoritative trust surface shows principal, exactly one stanza, mandate state/expiry, Hermes Agent, local route, and no-fallback policy. Rich terminals receive a restorable multiline composer (Enter submits, `Ctrl+J` inserts a newline, Up/Down history, `Ctrl+R` reverse search, bracketed paste that keeps normalized multiline clipboard text in one guarded submission, empty-input `?` help); `AEGIS_ACCESSIBLE=1` or `TERM=dumb` selects a stable line-oriented accessible/plain profile. Model text remains explicitly `Hermes model / untrusted`, passes through the centralized ANSI/OSC/control/bidi sanitizer before layout, and cannot populate authoritative approval or trust fields. Local slash directives and exact `quit`/`exit` aliases remain under Aegis custody, and high-confidence credential pastes are blocked before any model path. Ordinary prose containing those words remains a normal turn. EOF, session expiry, signals, runtime/proxy/model failures, and explicit exit converge on one bounded reverse-order cleanup path.

The authenticated manager's canonical local base vocabulary is `/help /status /context /authority /limits /scan /watch /findings /investigate /timeline /report /audit /cancel /clear /exit`; `/quit` aliases `/exit`. The manager advertises the discoverable bounded Agent Registry extension `/agents readiness|list|show|import hermes default|prepare|register` in both conversational and degraded headers; `/help agents` gives the exact grammar. `/agents import hermes default` prepares a deterministic non-authorizing proposal, and `/agents import hermes default confirm REVISION_DIGEST` imports only after the exact displayed digest is repeated. General preparation is likewise non-authorizing, registration requires the exact prepared revision digest, and successful mutation returns exact authoritative readback. One typed registry drives parsing, help, completion, lifecycle availability, canonical policy/audit names, and result schemas. Proposal and non-canonical envelopes remain buffered until complete validation. Rich terminals update one in-place turn indicator, while plain terminals print at most one progress line per turn. The Aegis-native core scan is bounded to manager identity/authority, Hermes discovery, effective configuration and scope, local route/readiness, and audit verification. It is not a host scan. Host process/network/file/persistence/dependency/sensor forms and `/watch` are truthful typed unavailable boundaries because no production adapters or leased source manager are installed. Low-ambiguity natural requests to list local Hermes profiles or import the default profile are intercepted by Aegis before model dispatch. The read-only inventory resolves only the configured operating-system principal's canonical `~/.hermes` and direct named-profile directories, validates owner/type/write-mode without following symlinks, caps enumeration at 256 entries, and returns sanitized stable descriptors without profile contents. Default-profile import additionally requires a real owner-matching, non-group/world-writable, non-empty `~/.hermes/config.yaml` no larger than 1 MiB. It never reads or hashes marker bytes; it derives a deterministic proposal with principal-stable Agent/fleet/source identities and a metadata-bound revision digest, persists an immutable disabled revision only after exact-digest confirmation, verifies exact readback, and is idempotent for exact replay. It never copies profile contents, provisions or modifies Hermes, launches a runtime, issues a mandate, activates the Agent, or grants credential/model authority.

The manager routes complete Aegis-owned operational facts before untrusted model inference. This includes Agent Registry prepare/count/list/show behavior, exact Hermes skill installation guidance, the fact that Registry import does not copy profile skills or configuration, and immutable Agent-ID versus unsupported display-alias semantics. These routes remain read-only or use the existing digest-confirmed transaction; ordinary text does not install skills, rename identity, or grant authority. Gateway manager sessions are bounded by the authenticated principal expiry rather than the browser-console session TTL. At that boundary Aegis destroys the disposable runtime and reports normal expiry with instructions to start a fresh authenticated session; it does not silently renew or resume expired authority.

Download progress is streamed, cancellation is safe to resume, and the downloaded registry name is not trusted as identity: Aegis rediscovers the artifact, binds its exact digest, then runs certification separately. No cloud fallback, silent model switching, normal Hermes-profile mutation, or external authority/systemd provisioning occurs.

`aegis reset` is the destructive, principal-authenticated development/testing path for replaying first run. It prints the execution profile plus a deterministic path-by-path plan, preservation list, and the required gateway stop-and-purge action. A development binary may reset only the exact ignored `<repository>/.aegis` subtree without an authority-passphrase prompt, but still requires explicit `yes` at a real-terminal default-deny `[y/N]` prompt. A release binary may reset only canonical `~/.aegis` or one exactly selected former/XDG migration source and always authenticates a verifiable passphrase-file authority once before confirmation and independently a second time after `yes`, immediately before apply. After authorization and confirmation, reset validates and disables/stops/removes only the exact current Aegis-owned `systemd --user` gateway unit, reloads the user manager, verifies unit-file removal, and only then deletes reset state with configuration last. An absent unit file is accepted only when systemd reports the exact unit `not-found` and `inactive`; a loaded, active, foreign, byte-drifted, unverifiable, or unsuccessfully purged gateway fails closed and preserves reset state. Success reports whether a gateway was purged. It reauthenticates and revalidates the complete reset plan immediately before deletion. It inventories only recognized, securely owned artifacts under a validated operator-home scope; unknown files, symlinks, hard links, ownership/mode failures, repository paths, and plan or identity drift deny before deletion. The narrow exception permits recognized Badger files inside an already previewed Aegis-owned Badger directory and recognized lifecycle-marker transitions directly inside an already previewed `persistence/authority-v1` or `persistence/fleet-v1` directory: reset regenerates the closed inventory, binds deletion to fresh identities, and still rejects unknown names or content outside those previewed directory scopes. Exact legacy defaults are also reset safely beneath group-writable XDG parents using descriptor-anchored no-follow operations; unsafe external parents are never chmodded or treated as artifacts, and an empty legacy child may be truthfully retained. `aegis migrate-layout` performs the separate real-TTY, digest-bound Linux migration from one exact former/XDG source into `~/.aegis` and accepts Enter at its displayed `[Y/n]` default after a complete copy/preservation plan; source cleanup occurs only after destination publication and verification. See [Path layout](docs/PATH_LAYOUT.md) and the [quickstart reset procedure](docs/QUICKSTART.md#reset-and-replay-onboarding).

Local-model onboarding is deterministic application code. `aegis manager model candidates` lists the closed candidate registry and confirms there is no default; `model route` previews managed versus external-local ownership; `model discover --endpoint LOOPBACK_URL` inspects only already-installed Ollama artifacts; and `model configure CANDIDATE_ID --endpoint LOOPBACK_URL` prints the exact digest-bound mutation and ownership/copy implications, then requires literal `yes` before atomically replacing an existing secure valid configuration. It never pulls, downloads, imports, or copies a model and never activates an uncertified artifact. Bootstrap visibly auto-selects an exact sole approved installed candidate instead of presenting a one-item menu; multiple installed candidates have no selection default. `model status` reports configuration, artifact, and certification drift with the next exact command.

Live certification remains deliberately opt-in and is never part of default tests or startup. The generated configuration uses the validated 15-minute principal authority maximum and five-minute manager turn/Ollama request deadlines so the complete CPU-bound local corpus can finish without removing bounded execution. After selecting one discovered official candidate, explicitly run `aegis manager certify CANDIDATE_ID`. The command exercises the complete Hermes → authenticated proxy → Ollama path at the configured 64K context and publishes the mode-`0600` certification only if every semantic case passes, including a relevant manager-specific ordinary conversational reply and a truthful explanation that Aegis stores actual credential values through protected intake while the model receives metadata only. Certification uses the same tool-free manager inference path as runtime: the proxy removes only Hermes's semantically empty `tools: []` plus `tool_choice: "none"` decoration before Ollama and denies every non-empty or executable tool request. The provider receives the strict response contract with exact operation-specific proposal argument schemas, and security-critical cases verify their exact typed arguments rather than accepting only an operation name. A schema-valid reply whose sole failure is omitted required conversational content enters a bounded three-execution loop using direct, case-specific wording instead of repeating an ambiguous request until principal authority expires. Equivalent truthful storage-boundary wording is accepted rather than requiring one exact phrase. Other semantic failures, invalid output, timeout, cancellation, authority expiry, and protocol/transport failure abort immediately by default. `--continue-on-error` instead runs the remaining cases for diagnostics, except after context cancellation or authority expiry; it never weakens the all-cases-pass rule or saves a partial certification. Each turn is bounded by `manager.hermes.turn_timeout`, the complete run is bounded by the authenticated principal's remaining authority lifetime, and any exhausted run tears down the session, names the failed case and stable reason without rendering model output, writes no partial certification, and prints the exact retry command. Instruction or corpus changes invalidate prior certifications. When configuration names that exact installed digest and matching certification record, startup verifies Hermes/Ollama versions, artifact digest, certification identity, and 64K context, then starts the authenticated proxy and disposable safe-mode Hermes gateway. No real artifact was downloaded or certified by this repository change, so examples remain deliberately unconfigured.

## Charter representation

Charters are strict JSON and bounded to 1 MiB. Unknown fields, trailing data, and omitted policy blocks or nested policy fields are rejected. Every selector must explicitly constrain issuer and the MVP's trusted `local` control-plane environment and anchor a subject, principal, or exact claim; unsupported authentication methods and wildcard/duplicate selector values fail validation. Plan preview requires a freshly authenticated configured principal and the exact `local` environment. Approval binds one immutable plan ID plus SHA-256 over deterministic Go JSON serialization of the typed charter and complete typed provisioning plan; request, decision, apply, and recovery revalidate the corresponding charter, plan, runtime, and environment bindings. Stored charter bytes/digests and plan digests are recomputed before use. Review explicitly shows charter/plan digests, runtime details, complete effects, per-stanza toolsets, memory and credential scopes, approval semantics, warnings, and the full previous-revision diff. Revisions are immutable on disk. Duplicate stanza IDs, overlapping enabled selectors, wildcard authority/scope, delegation, cross-stanza flow, persistent profiles/homes, runtime extensions, and mismatched Hermes tool grants/toolsets are rejected.

In the MVP, a charter `grant.tools` entry is a Hermes toolset ID because toolsets are the hard runtime-registration boundary Hermes exposes. `grant.tools` and `hermes.toolsets` must match exactly. MCP and plugin provisioning is rejected. Operational launches pass only the selected model-provider environment binding (`provider:<provider>`). The separately enforced `github/read` scope is accepted only with `github.get_repository.v1` and is consumed by the optional local broker; it is not injected as a Hermes environment credential.

## Encrypted credential authority

Each manager runtime receives a digest-bound `aegis.platform.expertise.v2` projection covering Agent Registry, Loop, Graph, Queue, evidence/disposition, external authority, and credential separation. Certification and policy digests bind that exact projection. Generic and polite unqualified Agent-registration imperatives are intercepted authoritatively before model dispatch and prepare the disabled local Hermes default-profile proposal; only the exact digest-bound slash confirmation may register it. Complete Agent Registry count, list, and exact show requests through the supervised gateway likewise bypass the model and read authenticated Registry facts. Credential-create imperatives are intercepted separately. Authenticated credential count, list, filtered-search, and exact-reference value-read requests use the same deterministic typed authority dispatcher in both the in-process manager and supervised gateway; the gateway returns `AEGIS / authoritative` without asking the model to select, approve, or perform the read. Through the gateway turn endpoint, qualified or unsupported Agent requests receive deterministic `/agents` guidance; credential creation remains unavailable because that endpoint has no protected no-echo intake, so it returns deterministic protected-intake guidance rather than a model narration or generic 503. Manager turn failures otherwise use typed runtime-unavailable, authority-unavailable/invalid, timeout, protocol, and internal categories with bounded remediation.

Natural create requests—including `new cred named NAME`—execute locally without a model turn. Terse `new cred` prompts for a name before protected value intake; the name prompt accepts the name alone, a conversational `named NAME` reply, or the full `new cred named NAME` phrase, strips those prompt/command words rather than storing them in the reference, and visibly normalizes other human text to a hyphenated reference. Kind defaults deterministically and disclosure is always protected; the model is not asked to negotiate either field. Filtered metadata requests such as `show me all doppler secrets` execute as an authoritative `secret.search` with the supplied filter instead of degrading to an unfiltered list. Interactive manager credential results use readable labeled lists and detail views; non-interactive CLI command results remain structured JSON.

Protected intake accepts bracketed multiline paste as one opaque no-echo value: paste the complete credential block and press Enter, then repeat it for confirmation. A mismatch discards queued protected input before the manager composer resumes. Recognized create values entered at the ordinary composer are stripped and wiped, then collected again only at the protected prompt. High-confidence credential material is blocked before Hermes; arbitrary-text detection is defense in depth rather than complete DLP.

Explicit value requests such as `what is the value for credential: "bdp-dev"` and `I need to see the bdp-dev cred value` execute directly through authenticated Aegis authority. The value is rendered only in the terminal as an escaped quoted string; it is not sent to Hermes, and terminal scrollback remains outside Aegis cleanup.

Ctrl-D at an empty manager composer is a normal `terminal_eof` shutdown, not `runtime_failed`. Bounded teardown first closes the process-authorized inference proxy, then checks the external runner and requests unload only when it is still present before disposable Hermes cleanup; genuine verification failure remains visible.

Deterministic first-time create grammar includes natural `store`, `save`, `create`, and `make` imperatives. Explicit credential-value syntax that does not match a known create grammar fails closed and is neither retained nor sent to Hermes.

Aegis now includes the local administrative foundation for storing reusable secrets without persisting credential values. Bare onboarding defaults to an owner-only `0600` host KEK because the automatically installed rootless gateway must reopen custody noninteractively; the UI discloses that the same host account can read that key. Aegis initializes and verifies the deployment-bound encrypted bbolt database. Advanced custody still exposes a passphrase-encrypted KEK for explicitly interactive `serve` operation and externally delivered systemd credentials for deployments that integrate the credential into their own service unit. Automatic gateway installation rejects those advanced custody modes rather than publishing a unit that cannot open authority. Each immutable secret version is encrypted with a fresh DEK and XChaCha20-Poly1305 nonce; the DEK is independently wrapped by a versioned KEK. The database and custody files are mode `0600`, use fixed schema buckets and a finite writer-lock timeout, perform startup schema/structural/key checks, and support exact bindings, rotation, logical revocation, and consistent ciphertext backups. Follow the deterministic [credential-authority setup path](docs/CREDENTIAL_AUTHORITY_SETUP.md).

Principal-only administration is available through `aegis secret initialize|put|metadata|list|rotate|bind|revoke|backup`. In an authenticated manager session, explicit requests to count, list, create, or retrieve an exact credential value execute directly against typed Aegis authority operations without a model round trip. A clear imperative such as `store a cred named test` establishes the exact create metadata and proceeds to protected no-echo intake. If a user includes an inline value, Aegis strips it from presentation/history, wipes the captured bytes, and collects the value again only at protected intake; multiple supplied values are never selected. `what is the value for credential: "test"` performs an exact-reference decrypt and intentionally renders terminal-escaped plaintext only in the authenticated session. Durable records remain encrypted; value-read audit is metadata-only, retained TUI state is purged on close, and terminal scrollback remains outside Aegis cleanup. If no inline value is supplied, direct protected no-echo intake proceeds without a separate mutation approval. Create is insert-only and an existing reference fails atomically; replacement uses the separately confirmed rotation path, while revocation, binding, and deletion-like operations retain explicit approval. Model responses may not echo a tracked value, audit and receipts remain metadata-only, and closure invalidates the proxy, stops disposable Hermes, removes its home, clears retained presentation/history state, and only then finalizes the receipt. External-local mode requests and verifies exact-model unload; managed mode instead terminates its dedicated Ollama daemon, the stronger process boundary. External-local mode cannot promise forensic process-memory erasure. `put` and `rotate` retain deterministic CLI operation and protected `--stdin` support. Secret subcommand values are never accepted in argv or returned by those subcommands; explicit manager value retrieval is the separate authenticated terminal-only path described above. `metadata` and history do not decrypt. Host-file initialization is the built-in automatic-gateway route and is explicitly reported as same-account readable; production deployments that require stronger custody must provide and verify their own `LoadCredentialEncrypted` unit integration before selecting `custody: systemd`. Keep KEK/recovery material separate from database backups.

The optional Linux [session credential broker](docs/CREDENTIAL_BROKER.md) implements one narrow model-visible downstream path: `github.get_repository.v1`. It combines pathname-socket `SO_PEERCRED`, a short-lived exact-session capability, live mandate/runtime checks, and one `github/read` authority binding; it applies the credential inside Aegis and returns only sanitized repository metadata. For a stanza whose exact toolset is `aegis`, Aegis generates a disposable MCP configuration that launches only its hidden credential bridge, disables ambient project plugins, rules, skills, and inherited Hermes state, queries the live Hermes gateway, and fails launch unless exactly `mcp__aegis__github_get_repository` is registered. It is not GetSecret, a generic proxy, or a claim that all credentials are brokered. Existing Hermes provider authentication remains environment-backed. Fleet projections, production unit/identity provisioning, TPM recovery, and Infisical migration remain separate boundaries.

## Runtime behavior and limits

- Supported adapter range: Hermes Agent `>=0.18.0,<0.19.0`; installed version constraints in each charter are enforced.
- Design uses real `hermes --safe-mode --tui --toolsets no_mcp`, never `-z`/one-shot.
- Every operational session gets a new process and a unique disposable `HERMES_HOME`; manager sessions never reuse one another's home or inherit normal `~/.hermes`.
- The Linux built-in manager and certification route starts Hermes 0.18.x with the built-in empty `context_engine` TUI toolset and a fixed public parser-compatibility API-key string that grants no authority. (`no_mcp` is an MCP-selection sentinel, not a valid `HERMES_TUI_TOOLSETS` value.) The child initially blocks on an inherited one-shot pipe and cannot execute Hermes until Aegis acquires pidfd custody, records the current host boot identity, and durably binds that exact process to the loopback inference proxy. Only then does Aegis send a fixed non-secret release marker. Missing authorization, EOF, malformed release input, custody failure, or release-pipe failure kills and reaps the blocked process and removes its disposable home. The proxy also denies after process exit, across a host reboot, or when an accepted TCP connection is not owned by the custodied process. This process-binding control is Linux-specific and is not host or network confinement.
- Ordinary operational toolsets use safe mode, which disables inherited user config, project rules, memories, plugins, and MCP. The exact `aegis` broker toolset instead uses an Aegis-generated disposable configuration and direct Hermes gateway process because Hermes safe mode disables MCP; it disables ambient project plugins, rules, skills, and inherited state explicitly and registers no other toolset.
- Aegis resolves and records exact Hermes toolset IDs and fails closed if they differ from the approved mandate. Ordinary safe-mode sessions retain `toolset_verification: launch_arguments`. Broker sessions record `toolset_verification: exact_registered_aegis_bridge_tool` only after the active Hermes gateway reports one registered tool, `mcp__aegis__github_get_repository`.
- Revocation appends an authoritative revocation fact and terminates the recorded runtime PID; mandates and per-session authority contexts are not rewritten in place.
- Stanza changes and material authority changes require a newly issued mandate and a clean runtime session; Aegis does not switch or expand authority inside a running session.
- Hermes-home/process isolation is not a host filesystem, network, container, or VM sandbox. A charter granting `terminal` or `file` intentionally grants broad host-facing authority and must be reviewed accordingly.
- Persistent named Hermes profiles, gateways, services, cron, arbitrary plugins/MCP, and external provisioning actions are denied by the MVP provisioner.
- Provisioning creates only new deterministic Aegis-owned mapping files atomically. Durable in-progress receipts retain the exact plan digest, approval ID, and charter digest. Recovery removes a matching owned artifact only when the consumed approval still binds the same plan ID/digest, charter, runtime, and environment; missing or corrupt authority bindings and non-matching artifacts are preserved for manual review while the receipt is finalized as failed.
- Operational provider authentication must be named by the stanza as `provider:<provider>`, configured under `credentials.provider_auth.<provider>`, and present in its configured source environment variable. Aegis injects only that resolved binding into Hermes; ambient provider keys are not inherited. Design receives no provider credential unless `credentials.design_provider` explicitly selects a configured provider binding. Provider-authentication values are not persisted or included in command output, receipts, audit events, errors, or model prompts. This boundary is separate from operator-supplied credential values explicitly admitted to the trusted-local manager session described above.
- The optional bbolt credential authority is an administrative store plus the backing authority for the implemented local broker's one typed GitHub action. It is not a generic operational secret source and does not replace environment-backed model-provider authentication.
- A live design turn requires an explicitly selected provider credential available to the disposable Hermes process. Discovery and expected provider-authentication failure remain testable without a key.

## API

`aegis serve` runs Echo v5 in the foreground. It exposes `/livez`, `/readyz`, protected `/v1` routes for charter, design, plan, approval, provisioning, session, inspection, configuration, and audit workflows, and the fleet-control roots `/v1/agents`, `/v1/loops`, `/v1/graphs`, and `/v1/queue`. Those fleet routes use the same application services as the public `agents`, `loops`, `graphs`, and `queue` Cobra resources: they support principal-authenticated registration/publication/submission, exact reads, immutable collection reads through `loops list`, `graphs list`, and `queue list`, registered-runtime queue processing, and the manual authenticated controller-side queue lifecycle (`POST /v1/queue/:item/retry`, `cancel`, `expire`, `exhaust`, `revoke`) with distinct denied, unavailable, conflict, not-found, terminal replay, lease-not-expired, attempt-budget-exhausted, and repair-required outcomes. The authenticated browser console uses that same application boundary to render and operate the bounded Registry, Loop, Graph, Execution Queue, and metadata-only Credentials workflows documented above. Its inspectors expose exact revisions and digests, Loop/Graph validation facts, dependent-loop outcomes, ordered lifecycle timelines, claim/retry/cancellation records, and Queue item/projection/Graph-run/Loop-execution/attempt causality; each domain distinguishes an authoritative empty collection from unavailable or corrupt state. Browser mutations are closed typed operations with principal/session, exact-origin, CSRF, target, and fresh authority checks; browser input never grants authority. Durable manual retry/reclaim, cancel, expire, exhaust, and revoke primitives and the registered single-turn Hermes gateway adapter exist, but automated orchestration, general multi-node execution, and live-provider acceptance remain absent. The HTTP bearer token authenticates transport, not principal identity. Unix-socket mode derives caller identity from Linux `SO_PEERCRED` and maps it through the configured UID; bearer-only TCP callers cannot acquire principal authority. Optional TCP TLS 1.2+ is enabled by configuring both `api.tls_cert_file` and `api.tls_key_file`, but TLS without an identity mapper still does not grant principal authority. Source-level pre-authentication and subject-level post-authentication rate limits are applied without trusting `Forwarded` or `X-Forwarded-*` headers. The server has explicit header/read/write/idle/shutdown timeouts, request limits, request IDs, safe errors, panic recovery, structured logging, and authorization in shared services. The default listener is loopback-only.

Runtime authority is represented by canonical bounded domains rather than a mutable cross-domain aggregate. `core.Mandate` remains the authorization grant; every launched session receives one immutable `core.AuthorityContext`; revocation is a separate append-only fact. The canonical authority codec defines a closed activate/revoke/expire command vocabulary, immutable controller-authored facts, non-authoritative processing receipts, rebuildable projections, and durable derived outbox entries. The generation-managed Badger authority repository processes each accepted command in one transaction that writes the command, fact, receipt, current projection, and outbox entry. Exact retries return the replay-verified durable receipt without duplicating facts or outbox work; conflicting command-ID digests deny; failed transactions leave no partial authority result. Current projection and admission reads replay canonical command/fact history in the same read transaction and fail closed if stored derived records diverge. After replay and projection verification, the repository can return one immutable committed-authority position bound to the context ID, sequence, fact digest, and projection digest. Its internal canonical audit-delivery boundary consumes verified outbox entries in strict sequence and creates metadata-only evidence for each exact position; exact retries add no duplicate evidence, while gaps, substitution, or reordering deny. The grant-producing readiness read observes admission, the committed position, and audit evidence in one Badger snapshot and denies with `audit_delivery_lagging` until evidence reaches that exact boundary. Receipts, projections, outbox entries, audit evidence, model output, and runtime narration cannot grant or reconstruct authority. This command-processing boundary remains internal rather than a CLI/API mutation workflow, and existing application service paths are not yet migrated to it. Content-addressed runtime artifacts and claim-specific verification receipts are separate evidence, not authority or completion declarations. The removed experimental plumbing/GraphRun CLI and API routes are not compatibility surfaces.

Audit records are cross-process locked, hash-linked, and checked against Ed25519-signed checkpoints under the separately configurable `audit.checkpoint_dir`. Application services write through a narrow injectable audit-authority interface that is never passed to Hermes; the default implementation remains in-process. For stronger append separation, deploy that interface behind a separately supervised process/account and retain checkpoints on separately protected storage. The default local deployment is not an external transparency service.
