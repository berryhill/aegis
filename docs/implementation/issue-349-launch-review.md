## Native configuration integration and residual limits

Native execution requires separate operator approval of the trusted Go executable
and exact OUTER Doer-contract digest. Selected-file host consent cannot supply
that authority. A native-only configuration can retain the already qualified
installed local decision backend without changing the grant or downloading tools.

The config-bound Codex operational connection normally denies all configuration
drift. The additive native-trust accommodation is review-only: one appended typed
implementation block must reconstruct the exact predecessor commitment when
removed; source, opaque selector, account and principal remain identical. Existing
fresh preview/connect and append-only history are retained, with full current
configuration matching still mandatory for runtime use. Unknown or unrelated
drift cannot be repaired. No credential bytes or operator YAML are rewritten by
the connection service.

This does not add or claim atomic CAS against arbitrary same-UID configuration
writers. Supported owning-service operations use the existing service-local
serialization, exact snapshot/head revalidation and atomic no-replace generation
publication. Hostile/uncooperative host writers remain a documented limitation,
not a reason to disable the drift guard, edit metadata hashes or invent a second
state writer. Independent testing must check the actual supported boundary rather
than infer stronger cross-process protection from a process-local mutex.

Native Go tests and proposed source execute under the controller OS identity.
Declared-input materialization, minimal environment, offline dependency policy
and tool-free inference are not a filesystem/network sandbox or independent
attestation against the same OS user/root. Legacy nil-context/native and
selected-file results retain their historical policies and limits.
