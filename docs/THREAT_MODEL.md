# Aegis MVP Threat Model

## Scope and assets

The MVP protects principal identity, canonical charters, immutable registered-Agent provenance and revisions, immutable Loop and Graph definitions and validation records, exact Graph participant/Loop bindings and run snapshots, durable submission outcomes, queue/claim/run causality, content-addressed runtime output, verification receipts, terminal dispositions, stanza-specific authority, mandates, approval evidence, provider credentials, isolated Hermes state, provisioning artifacts, sessions, and audit history. It covers one configured principal, local Linux/CLI operation, and Hermes Agent `>=0.18.0,<0.19.0`.

## Actors

- Configured principal: trusted to approve exact authority.
- Authenticated non-principal subject: trusted only for matching stanzas.
- Hermes/model output: untrusted proposal and runtime output.
- Local attacker or compromised runtime: may supply prompts, request stanzas, alter writable files, or attempt process/credential access.
- Operator/deployment administrator: trusted to protect configuration, state, API token, TLS keys, and checkpoint retention.

The CLI/API transport boundary authenticates callers outside the model. Charter validation and stanza selection form the authorization boundary. Approval separates proposal from deterministic provisioning. Each Hermes process/home is a stanza-state boundary. The host kernel, filesystem, and network remain outside Aegis confinement.

## Primary abuse cases and controls

| Abuse case | Control | Residual risk |
|---|---|---|
| Prompt claims principal identity | OS identity/SO_PEERCRED only | Compromised OS account remains authoritative |
| Stanza flag, profile, display name, or prompt escalates authority | Only verified subject/method/issuer/environment selectors authorize; a request only narrows; zero/multiple deny; no grant union | A legitimately trusted issuer or administrator can still configure an overly broad exact selector |
| Malformed, overlapping, disabled, or stale stanza policy is used | Strict required-field validation, overlap rejection, stored canonical digest verification, mandate-to-stanza equality, and runtime zero/multiple denial | Same-account state replacement remains possible without a stronger deployment boundary |
| Malformed or prompt-influenced Loop structure is treated as executable truth | Immutable typed Loop revisions; strict bounded decoding; deterministic digesting; fail-closed validation; atomic durable revision + exact validation + audit publication; exact canonical replay binding; public CLI/API publication requires an authenticated principal and one freshly admitted exact authority context; the narrow worker accepts only one exact executable action and matching evidence claims | Lifecycle application, general Graph execution, and real Hermes worker integration are not implemented; persisted definitions and readiness results grant no authority and cannot make work executable |
| A Graph substitutes a participant/Loop revision, admits malformed coordination, rewrites historical run inputs, or leaves a partial submission or completion outcome | Exact identity/revision/digest bindings; deterministic codecs; authenticated fresh submission admission through shared CLI/API services; transaction-local definition resolution; atomic accepted-or-rejected outcome; the worker rereads exact snapshot/Graph/Loop records and denies unsupported shapes before claim; terminal persistence atomically validates claim, attempt, authority, artifact, receipt, transition, projection, and disposition causality; the extracted-binary proof checks durable denial and historical readback | Lifecycle activation, multi-node and automated lifecycle scheduling, and a real Hermes worker adapter are absent; the installed no-key proof does not make persisted lifecycle records authoritative or establish general production readiness |
| Two workers claim one item, or a claim/attempt is detached from queue and run causality | Fresh claim admission followed by one conflict-detecting transaction that resolves the exact queue item and Loop execution; requires available canonical timing, remaining attempt capacity, and exact succeeded dependencies; and atomically writes the bounded lease, numbered attempt, claimed transition, projection, active-claim binding, and audit fact | Scheduling remains internal to one process/account; there is no public worker protocol, distributed fencing token, or general multi-node scheduler |
| A stale worker completes after lease expiry, retry bypasses backoff or attempt limits, cancellation races claim, or a projection grants claimability | Completion requires the matching active claim before its half-open expiry; reclaim requires the matching expired claim and bounded future availability; retry preserves attempt count and claim creates the next number; cancellation accepts only queued or claimed state; each mutation atomically writes canonical facts, active-claim binding, projection, and audit; claim admission matches projection state to canonical attempt/retry/dependency facts | Automated reclaim/retry/cancellation scheduling, dirty-store recovery, and complete projection-rebuild tooling are not wired; same-account/root mutation and denial of service remain outside the application boundary |
| Runtime output, adapter failure, or model narration is treated as success | Runtime bytes are untrusted; empty/invalid output fails; output is stored by content digest; each required claim repeats admission and must produce a valid passing receipt bound to the exact artifact/action/run/owner/authority; successful disposition repeats admission and is atomically committed with evidence metadata and transition; the release-shaped installed proof exercises this path | The deterministic no-key adapter is not Hermes; the verifier and worker share one process/account; installed execution is not independent attestation or evidence custody |
| Model provisions its proposal | Design uses the empty `no_mcp` toolset, has no provisioning service, bounds requirements/proposal and charter import to 1 MiB, accepts exactly one proposal envelope, and requires strict Aegis import | Hermes process is not a host sandbox |
| Changed or substituted plan reuses approval | Plan preview requires fresh configured-principal authentication and the exact local environment; approval stores one immutable plan ID and complete typed plan digest, and request, decision, apply, and recovery revalidate the charter/plan/runtime/environment binding before atomic single use | Host admin can rewrite plan and approval state together |
| Team session receives principal key | Exact `provider:<provider>` scope and typed binding | Granted terminal/file tools can access ambient host resources |
| Ambient provider or proxy authority reaches Hermes | Minimal environment and explicit selected-provider injection outside the manager; the manager receives only a fixed non-secret parser-compatibility string | A deliberately selected provider credential remains present for design/operational launches that require it; the public manager compatibility string is readable but grants no authority |
| Tool surface exceeds charter | Toolset allowlist and exact launch arguments | No individual-tool post-launch attestation in Hermes 0.18.x |
| Revoked/expired runtime continues | Supervisor, process start token, process-group termination | Crash recovery depends on persisted PID identity and OS state |
| Runtime input, historical state, or model output widens authority or presents stale authority as current | One immutable per-session authority context is bound exactly to its canonical mandate, charter revision, runtime, and effective authority; each runtime effect requires a fresh authoritative admission decision for the exact context ID/digest; append-only revocation and half-open expiry deny stale use | Authority contexts persisted before a failed launch can remain as orphan evidence; they do not create a session or grant a running process authority, but transactional cleanup remains desirable |
| Malformed, replayed, reordered, substituted, cross-context, expired, or ambiguous lifecycle intent changes authority | Closed activate/revoke/expire command vocabulary; authenticated actor and half-open acceptance window; exact sequence/previous-digest preconditions; one-to-one command/fact identity; strict versioned codecs; controller-authored immutable facts; complete digest-linked replay; one Badger transaction for command, fact, receipt, projection, and outbox; exact-retry deduplication and conflicting-digest denial | Command processing is currently an internal repository boundary rather than a wired CLI/API workflow; same-account/root replacement remains outside the application boundary |
| A retry, derived-record substitution, or partial Badger write is mistaken for current authority | Exact command-digest receipt lookup; canonical prefix replay; receipt/fact/projection/outbox linkage; same-transaction publication; collision rollback; current projection and admission reread canonical history in one snapshot; stored projection or outbox divergence fails closed; committed positions are returned only after replay and projection verification | Badger atomicity and replay checks remain inside the same local account/filesystem trust boundary and do not provide independent tamper evidence |
| Canonical authority audit is missing, reordered, duplicated, substituted, or allowed to lag while a grant is produced | Strict-sequence verified authority outbox consumption; create-only deterministic metadata evidence bound to context, sequence, fact digest, projection digest, and outbox digest; exact retries emit no duplicate; grant-producing readiness compares the latest evidence with the replay-verified committed position in one snapshot and denies lag | Authority audit evidence shares the Badger store and local account/filesystem boundary with canonical authority; it is delivery evidence, not an independent transparency service or a new source of authority |
| Runtime output or a stored filename is treated as verification | Runtime output is stored by content digest; a claim-specific verifier rereads the blob and emits a receipt bound to artifact, action, run, owner, authority context, expected digest, verifier, and policy version | The verifier currently runs in the same process and uses the same local store/account; this is component separation, not independent attestation or separately protected evidence custody |
| A discovered current-fleet candidate is treated as authenticated or authorized | The fixture adapter is explicitly proposal-only; it scans no ambient profile, environment, credential, dashboard, or handoff state; public CLI/API registration requires the configured principal through the shared application boundary | Principal authentication does not authenticate fixture claims or grant runtime authority; same-account/root replacement remains outside the application boundary |
| Fleet-source identity is rebound, an Agent revision is overwritten/substituted, or disabled/retired state is bypassed | Registration binds one stable Agent ID and one immutable source identity to revision 1; strict canonical codecs and content digests reject malformed/substituted records; exact replay is idempotent while conflicts deny; sequential create-only publication forbids overwrite and post-retirement revisions; the durable public application path and snapshot resolution require exact ID/revision/digest and enabled state with no latest fallback | Lifecycle tooling and general scheduler behavior remain narrow; same-account/root replacement remains outside the application boundary |
| Provisioning escapes state or crashes | Typed effects, containment, symlink rejection, atomic create, and durable intent recovery that removes matching owned artifacts only while the consumed approval still has the exact plan/charter/runtime/environment binding | Same-account filesystem races are not a separate-user sandbox; missing/corrupt authority bindings and mismatching recovery artifacts require manual review |
| Audit is rewritten | Narrow audit-authority boundary, hash chain, signed retained checkpoints | Default in-process authority and locally retained checkpoints can be replaced together |
| Audit delivery is interrupted, reordered, duplicated, or its derived state is tampered with | ID/digest-bound durable outbox, canonical-prefix validation, projection-first idempotent reconciliation, bounded ordered delivery, fail-closed readiness, and canonical-chain-first projection verification/rebuild | Outbox and projection share the same local account/filesystem boundary as canonical audit; they are operational derived state, not independent retention or external anchoring |
| API token grants principal | Unix peer identity required | TCP principal identity is unavailable without a future mapper |
| Reusable transport material leaks through configuration, unit text, argv, environment, preview, or console onboarding | New onboarding generates 256 random bits into an absolute current-owner mode-`0600` single-link token file; configuration stores only its path; service preview/unit omit the value; `aegis console` uses it over the Unix socket and emits a separate short-lived single-use bootstrap | Same-account/root/kernel access can read process memory or the protected file; inline `api.token` remains a compatibility surface and should not be used for new service onboarding |
| A second daemon removes the active socket or concurrently opens authoritative stores | The daemon acquires a current-owner mode-`0600` single-link nonblocking `<unix_socket>.lock` before stale-socket inspection/removal; concurrent startup denies; store-backed CLI construction denies while the configured socket exists and has no direct-store fallback | Locks coordinate cooperating Aegis processes only; a malicious same-UID process or root can unlink paths or interfere, and stale socket presence can cause denial of service |
| Service installation silently creates persistent/root authority or takes over an existing unit | Separate complete transport and unit previews with bounded `[Y/n]` confirmations; exact apply-time configuration, plan, unit-digest, current-owner, single-link, and byte revalidation; only `systemctl --user`; no linger mutation; foreign-unit denial; uninstall removes only the exact expected unit | Default-yes confirmation reduces ceremony but does not replace exact drift checks; this is same-account supervision, not a separate service identity or sandbox; pre-existing linger can make the user manager survive logout and is reported rather than changed |
| Browser input, cookie possession, or a copied API bearer creates principal authority | Browser identity is never accepted; an existing authenticated principal mints a random single-use bootstrap through the protected API path; exchange is exact-origin; the volatile session is capped by source-subject expiry; every protected request rechecks principal freshness | A compromised authenticated browser or same-account process can act for the remaining short session lifetime; in-memory sessions are lost on restart and are not durable mandates |
| Cross-site request, script injection, clickjacking, or browser storage leaks console authority | Exact Host/Origin checks, `SameSite=Strict` path-scoped `HttpOnly` cookie, session-bound CSRF on mutations, restrictive CSP, frame denial, no-store, typed templ rendering, no browser-side HTML construction, a digest/provenance-checked self-hosted Datastar asset, and no local/session storage | Browser, extension, vendored dependency, or OS compromise remains outside this application boundary; ordinary displayed prose can still socially deceive an operator |
| Plaintext remote console transport exposes session or bootstrap material | Configuration rejects non-loopback HTTP origins and non-loopback plaintext listeners; non-loopback deployments require configured TLS | Loopback traffic and TLS key custody remain host/operator trust dependencies; TLS authenticates transport, not principal identity |
| Self-update installs a corrupted or unpublished archive | Fixed repository identity, published stable SemVer metadata, no API or untrusted download redirects, an allowlisted HTTPS GitHub release-asset redirect, no downgrades, bounded archive parsing, release checksum verification, atomic replacement; Git tags alone are ignored | GitHub release metadata and checksum delivery are one trust domain; no independent signature/transparency verification |
| Interrupted release is resumed from a moved or forged tag | Existing annotated tag signature, exact annotation/object/peeled commit, reproducible changelog-only commit, local-main and remote-main relationship, and tagged-source verification; no force push or tag recreation | Git signing trust and operator repository access remain release-authority dependencies; ambiguous states require manual review |
| Release packaging publishes the wrong platform binary, unsafe archive shape/mode, version, checksum, state-mutating first-run artifact, missing console dependency, or fleet binary that cannot complete the claimed thin vertical | One CI/release verifier cross-builds the four declared targets; requires every archive to contain exactly one root `aegis` regular file with mode `0755`; rejects traversal, links, extra members, and symlink-parent output paths; generates and verifies `SHA256SUMS`; extracts the native archive; checks the injected exact stable version; requires bare non-TTY first run under an isolated home to deny without creating `.argis`; runs that installed binary through accepted and rejected Registry/Loop/Graph/Queue/evidence/disposition paths; and verifies the extracted binary serves its self-hosted Datastar asset plus authenticated console surface | CI verifies one native executable at runtime; cross-compiled non-native archives are build/checksum evidence rather than execution on each target OS, the deterministic adapter is not Hermes, browser engines are not exercised, and GitHub remains the publication trust domain |
| Candidate acceptance tests a different binary, inferred decision, substituted runtime, or unsafe rollback target | Explicit stable version and exact clean source revision; strict bounded operator-supplied decision; canonical non-symlink Hermes identity; one digest-bound extracted native candidate reused for checks; replacement, exact rollback, and withdrawal rehearsed only in an empty repository-local workspace; evidence records no publication or production mutation | Local SHA-256 and path canonicalization are not publisher or operator authentication; the script records supplied intent but cannot authorize publication, prove every target natively, or prove remote withdrawal |
| First run or valid-config compatibility reconciliation guesses identity, publishes split operational state, or overwrites unsafe authority/configuration | One complete profile-owned layout before service construction; host-native current-user plus UID lookup and immediate pre-publication revalidation; exact preview; explicit default-deny confirmation; mode-0700 root/state; verified empty authority generation; no-replace atomic mode-0600 configuration link plus directory sync on first run; and distinct absent/malformed/insecure/partial/ambiguous states. A valid existing configuration can create only an exactly absent operational-authority generation after fresh principal verification and explicit terminal confirmation. Non-interactive and ordinary commands deny with exit 2 and no mutation; existing dirty, corrupt, markerless, symlinked, wrong-owner, insecure, ambiguous, or populated legacy state is preserved. Interrupted initialization resumes only from a valid empty generation | First-run publication spans authority and configuration rather than one filesystem transaction; the authenticated local account, root, or kernel can still authorize or replace same-account state |
| Fresh authority initialization silently coexists with or imports legacy JSON authority | One shared plan/apply/open classifier covers `mandates`, `authority-contexts`, `authority-revocations`, and `sessions`; only absent or recursively proven operator-owned mode-0700 directory-only trees pass, while populated, unreadable, symlinked, wrong-type, wrong-owner, or wrong-mode paths deny | Securely empty legacy directories may remain as inert names; same-account or root mutation after a check remains a host-filesystem risk |
| Authority startup or repository access selects malformed, substituted, cross-family, crash-unclean, or path-redirected Badger state | Staged no-replace generation publication, synced embedded store/schema/codec identity, digest-bound `ACTIVE`, strict marker decoding, explicit `CLEAN`/`DIRTY` lifecycle, Linux no-follow descriptor-relative marker and generation-tree mutation, one versioned length-delimited binary key registry, strict key/value identity checks, complete transition replay/root verification, atomic context/index and fact/root transactions, and atomic command/fact/receipt/projection/outbox processing | `DIRTY` is crash evidence, not automatic recovery or independent tamper proof; Badger transaction atomicity and descriptor anchoring do not protect against root or malicious writes through already-open same-account descriptors, and the store and markers share one local filesystem boundary |
| Concurrent maintenance, low disk, corrupt restore data, ambiguous rollback, derived-projection substitution, or garbage collection damages authority state | Shared open-store and exclusive maintenance `flock` leases; context cancellation; closed-clean marker and embedded-identity verification; fixed 256 MiB reserve beyond bounded candidate output; bounded strict backup codec with ordered registered canonical keys and SHA-256; logical import into a fresh inactive identity with projection rebuild from canonical replay; exact native recovery/activation/rollback targets; typed durable-selection outcomes; device/inode-revalidated descriptor-relative non-active-only collection; atomic no-replace publication | Reserve checks cannot prevent later exhaustion or quota changes; locks coordinate cooperating Aegis processes only; backups are not encrypted or signed, same-account/root mutation remains possible, SHA-256 does not authenticate a publisher, and whole-host rollback needs external detection |
| An unqualified persistence combination, substituted fleet path, incomplete lifecycle evidence, or cross-store partial result is treated as authority | Exact fail-closed matrix for Badger `v4.9.5` session authority plus separate fleet-definition and fleet-lifecycle planes, and bbolt `v1.5.0` credential custody, on Linux/amd64/ext4; fleet schema `fleet-v1` at the one shared `state/persistence/fleet-v1` root; exact writer-lock, mode, 256 MiB reserve, migration, and clean-or-verified-recovered readiness checks; pinned modules; engine-import and canonical-schema ownership tests; atomic submission/claim/retry/cancellation/terminal transactions; projection-basis validation; installed thin-vertical proof; derived-state and cross-store non-authority rules | Qualification covers only the documented single-Aegis-process combination; dirty recovery and automated lifecycle scheduling remain absent, the proof does not qualify cross-built macOS/arm64 artifacts, and same-account/root replacement remains outside the application boundary |
| Legacy defaults are stranded, silently merged, or deleted through a writable XDG parent | Literal `~/.argis` typed resolver; artifact-derived legacy-only detection; canonical/legacy ambiguity denial; authenticated digest-bound migration; device/inode-verified descriptor-relative cleanup | Automatic migration/reset cleanup is Linux-only; interrupted post-publication cleanup can leave canonical plus legacy artifacts requiring exact manual inspection |
| Database or local encrypted-KEK-file theft exposes stored values | Fresh per-version DEK/nonces, XChaCha20-Poly1305, separately wrapped DEKs, KEK outside database; bare onboarding wraps the random KEK with an Argon2id-derived key and XChaCha20-Poly1305 | Metadata is sensitive; an offline passphrase attack remains possible; plaintext host-file KEK plus database theft defeats separation; root, the kernel, a compromised account/terminal, or an active process can capture plaintext |
| Authority passphrase is exposed through terminal/model/logs or a malicious helper response | Static Aegis-owned pinentry chrome, direct executable selection, bounded Assuan pipes, percent decoding, minimal environment, metadata-safe errors, no secret argv/config/audit/TUI state, fresh create/confirm requests, and no-echo terminal fallback only before interaction | A compromised account, desktop session, selected pinentry executable, root/kernel, or process-memory reader can capture bytes; pinentry provides no hardware custody, sandbox, keyring, cache, or recovery |
| Ciphertext/version/context is swapped | Canonical AAD binds store, record, version, kind, KEK, algorithm, format, and purpose; startup key check | No TPM monotonic anti-rollback protection; whole-host backup rollback needs external detection |
| Wrong stanza or destination resolves a secret | Broker requires exact peer + session capability + active session/mandate + charter + agent + stanza + local deployment + `github/read` scope + `github-api` destination + active binding/version on every use | No host/network confinement; a compromised authorized runtime may misuse its permitted read action |
| Prompt turns the broker into secret retrieval or SSRF | One strict `github.get_repository.v1` schema; caller cannot select URL, header, scope, record, version, deployment, stanza, or destination; redirects/proxy environment disabled; sanitized response allowlist; generated MCP bridge accepts only owner/repository and launch verifies its sole registered tool | Configured downstream and DNS remain operator/network trust; direct runtime network paths are not confined |
| Capability or request is replayed by another local process | 256-bit short-lived capability digest plus exact SO_PEERCRED UID/GID and runtime PID/start-token ancestry; fresh bounded request IDs/deadlines reject duplicate or stale actions; termination/failure/expiry removes capability material | Same-host root/kernel can inspect process memory/files; production needs distinct service/runtime identities |

| Credential metadata is listed/searched, or a credential is created or explicitly retrieved in the authenticated manager | Principal authentication, deterministic low-ambiguity intent/filter/exact-reference parsing, direct metadata list/search through the typed authority, fail-closed blocking of explicit credential-value syntax when create grammar does not map it, direct typed authority execution without a model round trip, atomic insert-only create with duplicate-reference conflict, separately confirmed rotation/replacement, encrypted durable storage, active/revoked checks, terminal-control escaping, metadata-only audit, and retained-session-content purge | Metadata itself can be sensitive; the authenticated terminal and active same-account processes can observe retrieved plaintext; terminal scrollback, swap, core dumps, kernel/root capture, filesystem snapshots, and forensic zeroization are outside Aegis's guarantee |
| Slash text in model/tool/sensor/report/audit output invokes local control | Dispatch accepts only composer-origin submissions; exact lowercase bounded parser consumes recognized, unknown, and malformed command-position input before Hermes; typed untrusted events cannot re-enter dispatch | Sanitized prose may still socially suggest that the operator type a command; the operator remains responsible for explicit submission |

| A certification turn stalls or emits events after cancellation | Configured per-turn deadlines, principal-expiry overall deadline, a bounded three-execution loop with direct case-specific wording only for missing required conversational content, default immediate abort on other failures, cancellation/expiry stop even in explicit continue-on-error diagnostic mode, permanently poisoned interrupted gateway client, reverse-order cleanup, and atomic all-cases-success-only certification publication | Slow local hardware or repeated incomplete conversational responses can still exhaust short principal authority and require an explicit retry; diagnostic continuation costs additional local resources; Hermes events do not carry prompt correlation IDs |
| A same-UID process inspects the manager Hermes environment or copies its API-key-shaped value | Hermes 0.18.x receives only a fixed public parser-compatibility string; proxy authority is instead bound before Hermes execution to Aegis-retained Linux pidfd custody, current host boot identity, and the exact accepted TCP connection owned by that process | Copying the string grants no authority, but root/kernel or an attacker able to compromise the released custodied process can still act through that process; pidfd, boot-ID, and `/proc` connection verification are Linux-specific and fail closed elsewhere |
| Signal, EOF, or blocked intake leaves terminal/process/model state behind | Context-cancellable ordinary/protected intake, captured terminal-state restoration, one lifecycle state machine, reverse-order bounded idempotent cleanup, first-signal cancellation, and second-signal default termination | Forced second-signal or host kill can interrupt cleanup; managed runtime crash recovery remains bounded by retained Aegis metadata and operating-system process state |
| Onboarding silently selects, downloads, or mutates a model | Closed no-default registry, loopback installed-only Ollama discovery, immutable digest match, complete preview, explicit `[Y/n]` confirmation, configuration-digest recheck, strict validation, and atomic mode-0600 publication; certification and activation remain separate | Ollama metadata and the local operator remain trust dependencies; Aegis does not prove artifact provenance merely from a local digest |
| Development and release binaries collide or reset the wrong authority | Stable binaries outside a worktree select production `~/.argis`; executable placement inside the verified Aegis module/worktree root overrides an embedded clean tag and selects ignored repository-local `.aegis`; production-path denial; separate deployment identities; reset restricted to its exact profile layout | A deliberately modified binary can bypass application checks; profile separation and Git ignore are not a host sandbox |
| Reset follows a malicious path or erases external/operator state | Profile-bound target, host-native principal match, production double authentication with the existing 12+ byte authority passphrase when credential material is in scope, deliberate confirmation-only development reset, operator-home containment, repository rejection except for the exact development `.aegis` subtree, root/home rejection, no symlink following, owner/mode/link checks, closed artifact inventory, Aegis schema evidence, complete preview, explicit default-deny confirmation, immediate full-plan revalidation, descriptor-anchored device/inode-checked legacy deletion, and configuration-last ordering | Development intentionally trades passphrase reauthentication for rapid local reset; deletion is not one transaction across independent paths, and an interrupted reset may require exact inspection and recovery from a separate backup |

## Non-goals

The MVP does not provide host sandboxing, network confinement, multi-tenant isolation, formal information-flow tracking, hardware attestation, multi-party approval, externally anchored transparency, guaranteed plaintext zeroization/physical erasure, a generic credential bridge, a fleet projection system, or protection from a fully compromised kernel/operator account. The model-visible broker bridge supports only typed GitHub repository metadata.

## Deployment requirements

Protect production `~/.argis` and repository-local `.aegis` roots and their state with mode 0700, never copy authority material between profiles, keep API tokens/TLS keys outside source control, use Unix sockets for principal operations, and configure an exact HTTPS console origin plus TLS for any non-loopback browser deployment. Place the audit-authority interface behind a separately supervised process/account, retain audit checkpoints on a separately protected boundary, supervise Aegis externally, and review any stanza granting `terminal` or `file` as broad host-facing authority. Use only an explicitly qualified storage combination; the current post-Track-A envelope is Linux/amd64/ext4 with the exact versions and settings in `specs/STORAGE.md`, not every platform with a release archive. Keep the authority database on a local filesystem, keep KEK/recovery material out of its backup set, use only a trusted pinentry executable/session for foreground passphrase custody, prefer encrypted systemd credential custody for headless services, disable core dumps as an operator/OS control (Aegis does not enforce this), and encrypt ciphertext backups to offline recovery recipients before they leave the host.
